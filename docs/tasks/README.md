## 태스크 문서 규칙

각 태스크는 다음 섹션을 가진다. 순서를 지킨다.

1. **Summary** — 코드베이스를 모르는 사람 기준 2~3문장. "무엇을 만들면 끝인가".
2. **Scope** — 포함/제외를 명시적으로. 제외 항목에는 어느 태스크로 가는지 적는다.
3. **Acceptance criteria** — 번호를 매기고, 각 항목이 **검증 가능**해야 한다.
   "잘 동작한다" 는 기준이 아니다. "1초에 한 칸 내려간다" 가 기준이다.
4. **Out of scope / 하지 말 것** — 에이전트가 넘치게 일하는 것을 막는 울타리.
5. **Verification** — 어떻게 확인하고 무엇을 보고할지.

한 태스크는 한 스레드가 한 번에 끝낼 수 있는 크기여야 한다. 수용 기준이
10개를 넘으면 태스크를 쪼갠다.

## 태스크 문서를 쓸 때의 교훈

T-001 실행에서 실제로 나온 것들이다.

- **시간 대기를 검증 기준으로 쓰지 마라.** T-001 의 Verification 에 "30초간
  방치했을 때 게임 오버에 도달하는지"라고 썼다. 낙하 간격 1000ms 규정과
  산술적으로 양립하지 않는 기준이었고(30초면 조각 1~2개), 에이전트는 그것을
  문자 그대로 기다리다 턴을 소진했다. 검증은 **관측 가능한 상태**로 쓴다:
  "프로덕션 함수 stepDown() 을 반복 호출해 게임 오버 경로를 통과시킨다".
- **최종 출력 형식을 태스크에 못박아라.** "기준 N개 각각에 충족/미충족/미검증과
  근거를 한 줄씩" 이라고 지정해야 부모가 판정할 수 있는 산출물이 돌아온다.
- **"하지 말 것" 섹션이 실제로 작동한다.** 에이전트의 주된 실패는 태만이 아니라
  범위 초과다. 울타리가 없으면 Phase 0 에서 라인 클리어까지 만들어 T-003 의
  검증 지점을 없앤다.
- **"기존 코드에서 반드시 지킬 것" 섹션이 효과가 컸다.** T-002 는 실제 심볼
  이름(`collides`, `movedDown`, `CONFIG.SHAPES[id][rot]`)을 문서에 적었고,
  그 결과 자식이 기존 함수를 재사용하고 시그니처를 건드리지 않았다.
  T-001 처럼 추상적으로 썼다면 비슷한 함수를 새로 만들었을 것이다.
- **함정을 문서에 명시하면 검증 깊이가 달라진다.** T-003a 에 "SRS 표준표는
  y 가 위로 증가하니 부호를 그대로 옮기면 반대로 밀린다"고 적었더니, 자식이
  요구하지 않은 280 케이스 전수 대조를 스스로 했다. 함정을 적지 않았다면
  수용 기준 3(빈 보드에서 x·y 불변)은 `[0,0]` 오프셋 덕에 **부호가 틀려도
  통과**했을 것이다.
- **수용 기준에 초기 상태를 적어라.** T-003a 기준 6("70회 호출 시 각 10회")은
  bag 경계에서만 성립하는데 그 전제를 빠뜨렸다. 자식이 측정 조건을 명시하고
  넘어갔지만, 기준 자체가 불완전했던 것이다.
- **브랜치 이름을 추측하지 마라.** bb 는 스레드 제목을 슬러그화해
  `bb/<slug>-<threadId>` 를 만든다. 제목이 한글이면 슬러그가 짧아지고 ASCII 가
  섞이면 길어진다. 병합 대상은 `git worktree list` 에서 읽는다.
- **병렬 실행은 영역 분담으로 git 충돌을 없앨 수 있지만, 의미 충돌은 못 없앤다.**
  T-003b/c 를 동시에 돌렸고 `state` 삽입 위치와 함수 소유권을 문서로 나눈
  결과 git 자동 병합이 충돌 0건으로 성공했다. 그런데 T-003b 가 만든
  `lockTimerMs` 를 T-003c 의 `holdCurrentPiece` 가 초기화하지 않는 결함이
  남았다. **두 심볼이 한 파일에 공존한 적이 없어 양쪽 수용 기준 어느 쪽으로도
  잡히지 않는다.** 병렬 병합 뒤에는 반드시 통합 리뷰를 따로 한다:
  "한쪽이 만든 상태를 다른 쪽이 건드리는 지점"을 목록으로 뽑아 확인한다.
- **디자인은 자기 보고로 판정할 수 없다.** T-004 는 13개 기준을 전부 "충족"
  으로 보고했고 실제로 다 맞았지만, 스크린샷을 직접 봐야만 보이는 것들이
  따로 있었다(하단 죽은 공간, 빈 HOLD 박스). 측정 가능한 기준은 자식이
  증명할 수 있어도, **구성(composition)은 부모가 눈으로 봐야 한다.**
- **측정할 수 없는 기준은 설명을 요구해 판정 가능하게 만든다.** T-004 기준 7
  "게임오버와 일시정지가 서로 다른 시각적 상태다" 에 "무엇이 다른지 한 줄로
  설명하라" 를 붙였다. 같은 오버레이에 글자만 바꾸면 그 한 줄을 쓸 수 없다.
  실제로 청록 유리(blur) vs 적색 침수(불투명)로 갈렸다.
- **브라우저로 검증할 때 이벤트 전파를 확인하라.** `new KeyboardEvent(...)` 는
  기본이 `bubbles: false` 다. 리스너가 `window` 에 있는데 `document` 에서
  dispatch 하면 도달하지 않는다. 코드 결함으로 오인하기 쉽다.
- **T-002 는 한 턴에 끝났다.** T-001 은 시간 대기로 턴을 소진해 스티어링이
  필요했다. 차이는 코드 난이도가 아니라 태스크 문서의 Verification 절이었다.
