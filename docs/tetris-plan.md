# Tetris (single-player, single-file) — 구현 계획

Status: Draft — 관련 태스크: `docs/tasks/T-001` ~ `T-005`

## Goals

1. 표준 테트리스 가이드라인(7-bag, SRS, 홀드, 고스트, 락 딜레이)을 따르는
   1인용 게임을 **단일 HTML 파일**로 제공한다. 빌드 단계도 서버도 없다.
2. 게임 로직을 렌더링/입력에서 분리해, 규칙 변경이 그리기 코드를 건드리지
   않게 한다. 회전 시스템은 교체 가능한 데이터 테이블로 둔다.
3. 프레임레이트와 무관하게 낙하 속도가 동일하고, 320px 화면에서도 조작
   가능하다.

## Layer model

| 레이어 | 책임 | 이 레이어가 모르는 것 |
|---|---|---|
| CONFIG | 보드 크기, 속도 커브, 점수표, 타이밍 상수 | 전부 |
| LOGIC | 보드 배열, 충돌, 회전+월킥, 라인 클리어, 점수 | canvas, DOM, 키보드 |
| STATE | 현재 조각, 큐(7-bag), 홀드, 레벨, 락 딜레이 타이머 | 그리기 방법 |
| RENDER | canvas 드로잉, 사이드 패널 DOM 갱신 | 규칙 |
| INPUT | 키보드 DAS/ARR, 터치 제스처 → 의도(intent) 변환 | 규칙 |
| LOOP | 델타 타임 누적, 상태 전이 오케스트레이션 | 세부 규칙 |

INPUT은 규칙을 실행하지 않고 `{type:'move', dx:-1}` 같은 **의도**만 만든다.
LOOP가 그 의도를 LOGIC에 적용한다. 그래서 키보드와 터치가 같은 경로를 쓴다.

## 핵심 자료구조 계약

```js
// 보드: 22행(상단 2행은 스폰 버퍼) x 10열. 0 = 빈칸, 1~7 = 조각 종류 id.
board: Uint8Array(22 * 10)          // 인덱스 = row * 10 + col

// 조각: 회전 상태는 0~3. 모양은 CONFIG의 테이블에서 조회한다.
piece: { id: 1..7, rot: 0..3, x: number, y: number }

// 상태 갱신은 순수 함수. 원본을 변형하지 않는다.
lockPiece(board, piece) -> { board: 새 보드, clearedRows: number[] }
tryRotate(board, piece, dir) -> piece | null   // null = 월킥 5회 모두 실패
```

규칙:
- 좌표계 원점은 보드 좌상단, y는 아래로 증가한다. 스폰 y는 버퍼 안이므로 음수가 아니다.
- `tryRotate` 실패는 예외가 아니라 `null`이다. 회전 실패는 정상 게임 상태다.
- LOGIC 함수는 시간을 모른다. 락 딜레이 타이머는 STATE와 LOOP의 책임이다.

## 회전과 월킥

SRS 오프셋 테이블을 데이터로 둔다: `KICKS.JLSTZ[from][to]`, `KICKS.I[from][to]`,
각 5개 `[dx, dy]`. O 조각은 회전하지 않는다. 코드에 회전 분기를 넣지 않고
테이블 조회 실패 시 회전 자체를 no-op으로 만든다.

## 타이밍

| 항목 | 값 | 근거 |
|---|---|---|
| 락 딜레이 | 500ms, 이동/회전 시 리셋, 최대 15회 | 표준. 무한 스핀 방지를 위해 리셋 횟수 상한이 필수 |
| DAS | 167ms | 첫 반복까지의 지연 |
| ARR | 33ms | 반복 간격 |
| 낙하 | 레벨별 커브 테이블 | 프레임 수가 아니라 ms로 저장해 rAF와 무관하게 |

## Phases

- **Phase 0 — 뼈대.** CONFIG, 보드 배열, canvas 렌더, 고정 속도 낙하, 충돌.
  플레이는 못 하지만 조각이 떨어지고 쌓인다. (T-001)
- **Phase 1 — 조작.** 좌우/소프트드롭/하드드롭, DAS/ARR, 회전(월킥 없는 단순
  회전). 여기까지가 "게임". (T-002)
- **Phase 2 — 규칙 완성.** SRS 월킥, 7-bag, 홀드, 고스트, 락 딜레이, 라인
  클리어 점수, 레벨. (T-003)
- **Phase 3 — 마감.** T-스핀/B2B/콤보, 사이드 패널 UI, 최고 점수 저장,
  일시정지/게임오버 오버레이, 모바일 터치. (T-004, T-005)

각 Phase 끝에서 브라우저로 실제 실행해 확인한다. Phase가 끝나기 전에 다음
Phase의 코드를 미리 넣지 않는다.

## Decision points

1. **보드를 `Uint8Array`로 둘 것인가, 2차원 배열로 둘 것인가?**
   권장: `Uint8Array` 1차원. 복사가 `.slice()` 한 번이라 순수 함수 갱신이 싸다.
   2차원은 매 복사마다 22개 배열을 만든다.
2. **락 딜레이 리셋 상한을 15회로 둘 것인가?**
   권장: 둔다. 상한이 없으면 무한 스핀으로 게임이 끝나지 않는다.
3. **T-스핀 판정을 3-corner 룰로 할 것인가?**
   권장: 한다. 킥 기반 판정보다 구현이 짧고 표준에 충분히 가깝다.
4. **점수/최고점수를 localStorage에 둘 것인가?**
   권장: 최고 점수만. 진행 중 상태 저장은 범위 밖(YAGNI).
5. **디자인 방향은?**
   권장: 다크 네온 아케이드. 단, 결정은 T-004에서 확정하고 그 전엔 무채색.

## Implementation notes

- `Uint8Array`는 `.slice()`가 새 배열을 반환하므로 불변 갱신과 잘 맞는다.
- 낙하 속도를 프레임 수로 저장하면 120Hz 모니터에서 2배 빨라진다. 반드시 ms.
- `document.hidden` 시 자동 일시정지. 탭 복귀 시 델타 타임이 수 초로 튀는 것을
  막는다. 이건 기능이 아니라 델타 타임 설계의 필연적 귀결이다.
