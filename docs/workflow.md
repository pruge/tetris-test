# bb 기반 개발 워크플로

이 문서는 이 저장소에서 T-001 ~ T-003c 를 실제로 실행하며 확인한 절차다.
추측이 아니라 겪은 것만 적는다. 겪지 않은 것은 "미검증"으로 표시했다.

## 0. 개념 매핑

bb 에는 "태스크" 라는 1급 개념이 없다. 실행 단위는 **thread** 다.

| 우리가 부르는 것 | bb 에서의 실체 |
|---|---|
| 계획 | `docs/tetris-plan.md` (문서) 또는 `--plan` (런타임 승인 모드) |
| 태스크 정의 | `docs/tasks/T-*.md` (문서) |
| 태스크 실행 | thread (`bb thread spawn`) |
| 작업 공간 | environment = managed worktree |
| 규약 | `.bb/AGENTS.md` (git 추적 필수) |

## 1. 문서의 층위와 작성 시점

**구조는 미리, 상세는 직전에.**

| 문서 | 시점 | 이유 |
|---|---|---|
| 계획 문서 | 선행, 전부 | 레이어 경계와 자료구조 계약은 나중에 바꾸면 쓴 코드를 다 뒤집는다 |
| 태스크 **목록** | 선행, 전부 | 의존 관계와 Phase 경계를 못 보면 태스크를 잘못 자른다 |
| 태스크 **본문** | 착수 직전, 하나씩 | 앞 태스크의 실제 코드를 봐야 정확한 기준을 쓸 수 있다 |

근거: T-001~T-005 본문을 한 번에 썼다면 T-001 의 "30초 방치" 결함이 5개
문서에 복제됐을 것이다. 또 T-002 본문에 적은 실제 심볼 이름(`collides`,
`movedDown`, `CONFIG.SHAPES[id][rot]`)은 T-001 이 끝나기 전에는 존재하지도
않았다.

예외 — 한 번에 다 써도 되는 경우: 태스크가 서로 독립적일 때, 외부에 전체
범위를 약속해야 할 때, 태스크가 3개 이하일 때.

## 2. 계획 문서 서식

```
Status / 관련 태스크
## Goals            번호 매긴 3개 내외. 전략적 의도만.
## Layer model      표로 분해. "이 레이어가 모르는 것" 열이 핵심이다.
## 핵심 자료구조 계약  코드 블록 + 불변 규칙. 실패를 예외로 할지 null 로 할지까지.
## <세부 메커니즘>    회전, 타이밍 등 영역별
## Phases           산출물 기준으로. "1주차" 가 아니라 "Phase 1: 조작".
## Decision points  미결 질문 + 각각의 **권장안**
## Implementation notes  함정과 그 근거
```

Decision points 가 가장 값어치가 컸다. `Uint8Array` vs 2차원 배열을 미리
정해뒀기 때문에 자식 스레드가 그 논의를 다시 하지 않았다.

## 3. 태스크 문서 서식

```
Phase / Status / Depends on (커밋 해시까지)
## Summary               코드베이스를 모르는 사람 기준 2~3문장
## 병렬 작업 주의         (병렬일 때만) 영역 분담
## 기존 코드에서 반드시 지킬 것   실제 심볼 이름으로
## Scope                 포함 / 제외(어느 태스크로 가는지 명시)
## Acceptance criteria   번호. 각 항목이 측정 가능해야 한다.
## Out of scope / 하지 말 것
## Verification          어떻게 확인하는가
## 최종 출력 형식         정확히 N줄, 형식 지정
```

### 수용 기준을 쓰는 법

- **측정 가능해야 한다.** "잘 동작한다" 는 기준이 아니다.
  "1초에 한 칸 내려간다" 가 기준이다.
- **초기 상태를 함께 적어라.** T-003a 기준 6("70회 호출 시 각 10회")은
  bag 경계에서만 성립하는데 그 전제를 빠뜨려 자식이 보충해야 했다.
- **회귀 항목을 넣어라.** 마지막 기준은 "앞 태스크의 기준 N 이 여전히
  성립한다" 로 둔다. 태스크가 쌓일수록 이게 중요해진다.
- **10개를 넘으면 태스크를 쪼갠다.**

### 함정을 명시하면 검증 깊이가 달라진다

T-003a 에 "SRS 표준표는 y 가 위로 증가하니 부호를 그대로 옮기면 반대로
밀린다" 고 적었더니 자식이 요구하지 않은 280 케이스 전수 대조를 했다.
그 경고가 없었다면 수용 기준 3(빈 보드에서 x·y 불변)은 `[0,0]` 오프셋 덕에
**부호가 틀려도 통과**했을 것이다. 기준만으로는 못 잡는 결함이 있다.

### Verification 에 시간 대기를 쓰지 마라

T-001 의 유일한 실패 원인이었다. "30초 방치" 라고 썼더니 에이전트가 문자
그대로 기다리다 턴을 소진했다. 관측 가능한 형태로 쓴다:
"프로덕션 함수 `advance(deltaMs)` 를 직접 호출해 ms 를 주입한다".

### 최종 출력 형식을 못박아라

`N. 충족|미충족|미검증 — <근거>` 형식으로 정확히 N줄을 요구한다.
부모가 판정할 수 있는 산출물이 돌아온다. T-001(형식 미지정)은 자유 서술이
돌아왔고, T-002 이후는 전부 지정 형식을 지켰다.

## 4. 스레드 운영

```bash
# 배정 — 사양은 프롬프트가 아니라 저장소에 있다
bb thread spawn --project <id> --parent-self \
  --new-environment worktree --base-branch main \
  --provider claude-code --title "T-00X ..." \
  --prompt "docs/tasks/T-00X-....md 를 읽고 구현한다. ..."

bb thread wait <id> --status idle --timeout 1800
bb thread output <id>
bb thread archive <id> && bb thread stop <id>
```

프롬프트에 사양을 적지 않는다. 프롬프트의 사양은 재실행하면 사라지고,
저장소의 사양은 남는다. 프롬프트에는 **어느 문서를 읽을지**와 **이번에
특히 조심할 것**만 적는다.

### 스레드가 기대대로 안 끝났을 때

| 상황 | 명령 |
|---|---|
| 턴이 실패해 `error` | `bb thread retry <id>` — 타임라인 중복 없이 재제출 |
| 덜 끝났고 컨텍스트는 살릴 가치가 있음 | `bb thread tell <id> --mode auto` |
| 접근 자체가 틀림 | `bb thread edit-message` (이후 턴 폐기, 워크스페이스 변경은 유지) — 미검증 |
| 다른 방향도 같이 보고 싶음 | `bb thread fork <id>` — 미검증 |

T-001 이 `idle` 인데 미완이었다. `error` 가 아니므로 retry 대상이 아니다.
`--mode auto` 로 스티어링했다. `--mode queue` 였다면 idle 스레드라 대기만
하고 아무 일도 일어나지 않았을 것이다.

## 5. 리뷰

`docs/CODE_REVIEW.md` 의 원칙: 변경된 동작 범위 안에서 "무엇이 깨지는가,
가장 작은 수정은 무엇인가".

**자식의 자기 보고를 그대로 믿지 않는다.** 확인하는 것은 주로 구조다:

- 지시한 분리가 실제로 존재하는가 (`grep "type: '"` 로 의도 객체 확인)
- 범위 밖 기능이 몰래 들어오지 않았는가 (`grep -niE "tspin|score|hold"`)
- 순수 함수가 원본을 변형하지 않는가 (소스에서 `.slice()` 확인)
- 데이터 테이블이 표준과 일치하는가 (SRS 킥 16쌍 직접 대조)

동작 수치(x 가 3→2 로 변한다)는 자식의 관측을 신뢰했다. 구조가 맞으면
수치는 따라온다는 판단이지만, **그건 검증이 아니라 추론이다.**

### 디자인은 눈으로 봐야 한다

T-004 는 13개 기준을 전부 충족했고 실제로 다 맞았다. 그런데 스크린샷을
직접 보고서야 보이는 것이 따로 있었다(보드 하단 170px 죽은 공간, 빈 HOLD
박스가 만드는 구멍). **측정 가능한 기준은 자식이 증명할 수 있지만
구성(composition)은 부모가 봐야 한다.**

측정할 수 없는 기준은 **설명을 요구해서** 판정 가능하게 만든다. T-004 기준 7
"게임오버와 일시정지가 서로 다른 시각적 상태다" 에 "무엇이 다른지 한 줄로
설명하라" 를 붙였다. 같은 오버레이에 글자만 바꾸면 그 한 줄을 쓸 수 없다.

### 브라우저 검증의 함정

`new KeyboardEvent('keydown', {key:'p'})` 는 기본이 `bubbles: false` 다.
리스너가 `window` 에 있는데 `document` 에서 dispatch 하면 도달하지 않는다.
일시정지가 안 걸리길래 결함으로 의심했지만 주입 방식이 틀린 것이었다.
**결함을 보고하기 전에 자기 관측 방법부터 의심하라.**

## 6. 병합

```bash
BR=$(git worktree list | grep t-00X | sed 's/.*\[\(.*\)\]/\1/')
git merge --no-ff "$BR" -m "merge: T-00X ..."
```

**브랜치 이름을 추측하지 마라.** bb 는 스레드 제목을 슬러그화해
`bb/<slug>-<threadId>` 를 만든다. 제목이 한글이면 슬러그가 짧아지고
ASCII 가 섞이면 길어진다. `git worktree list` 에서 읽는다.

병합 후 `docs/tasks/README.md` 의 상태를 갱신하고, 리뷰에서 나온 후속
항목을 새 태스크로 등록한다.

### 병합과 정리의 순서

**병합을 먼저 하고 archive 한다.** archive 하면 worktree 디렉터리가 통째로
사라져 `git worktree list` 에서 브랜치 이름을 읽을 수 없고, 미커밋 변경은
회수할 수 없다. 자식이 커밋을 남겼는지 확인한 뒤 archive 하라.

| 대상 | archive 후 |
|---|---|
| `~/.bb/worktrees/env_*/` 디렉터리 | **완전 삭제** |
| `git worktree list` 등록 | 제거 |
| 환경 레코드 | `destroyed` 로 남음 (조회만 가능) |
| `bb/<slug>-<threadId>` 브랜치 | **남는다** — 작업 결과물이므로 |
| 스레드 타임라인·최종 출력 | 남는다 |

브랜치는 bb 가 정리하지 않는다. 병합이 끝났으면 `git branch -d` 로 직접
지운다. worktree 안에서만 만든 로그·산출물은 함께 사라지므로, 남겨야 할
것은 커밋하거나 밖으로 내보낸다.

### 환경 회수

`bb thread archive` 가 환경 회수를 유발한다. 환경은
`ready → retiring → destroyed` 로 가고 worktree 가 사라진다. **비동기이고
수 분이 걸릴 수 있다.** 폴링해서 안 끝났다고 실패로 판단하지 마라.

archive 를 빠뜨리면 환경이 `ready` 로 남아 worktree 가 계속 쌓인다. 실제로
T-003a 는 병합 실패로 `&&` 체인이 끊겨 archive 가 실행되지 않았고, 한참
뒤에야 발견했다. **여러 명령을 `&&` 로 묶으면 앞이 실패할 때 뒤가 조용히
건너뛰어진다.** 정리 명령은 별도로 실행하거나 `;` 로 분리한다.

상태 확인: `bb environment show <id>`, `git worktree list`,
`bb thread list --project <id>` (archive 여부는 Status 열의 `(archived)`).

## 7. 병렬 실행

두 태스크가 **서로 다른 함수를 건드릴 때만** 병렬로 돌린다. 기능 목록이
아니라 코드 이음매로 자른다.

태스크 문서에 "병렬 작업 주의" 섹션을 넣고 다음을 지정한다:

- 공유 객체(`state` 등)의 **삽입 위치를 서로 다르게** — 다른 hunk 가 되도록
- 함수 소유권 — "이 함수는 네 영역", "저 함수는 건드리지 마라"
- 불가피하게 겹치는 한 줄은 미리 지정하고 "충돌해도 예상된 것" 이라고 적는다

결과: T-003b/c 를 동시에 돌려 **git 충돌 0건**으로 자동 병합됐다.

### 그러나 git 충돌 0건이 통합 성공은 아니다

T-003b 가 만든 `state.lockTimerMs` 를 T-003c 의 `holdCurrentPiece()` 가
초기화하지 않는 결함이 남았다. 두 자식 모두 자기 수용 기준을 100%
충족했고 git 도 충돌을 보고하지 않았다. **두 심볼이 한 파일에 공존한 적이
없었기 때문**이다.

**병렬 병합 뒤에는 반드시 통합 리뷰를 한다.** 방법:
한쪽이 만든 상태 필드를 다른 쪽이 건드리는 지점을 목록으로 뽑고, 각각
초기화·갱신 책임이 누구에게 있는지 확인한다.

### 병렬화의 상한은 아키텍처가 정한다

`.bb/AGENTS.md` 가 "단일 HTML 파일" 을 못박고 있어 두 스레드가 같은 파일을
쓸 수밖에 없었다. 모듈이 나뉜 프로젝트라면 영역 분담 조항 자체가 불필요하고
통합 결함 가능성도 낮다.

## 7.5 테스트

테스트는 세 층에 걸쳐 있다. 한 층이라도 비면 안 남는다.

| 층 | 무엇을 |
|---|---|
| `.bb/AGENTS.md` | "모든 태스크는 테스트를 남긴다" 는 규약. 모든 스레드에 자동 주입되므로 태스크 문서마다 반복하지 않는다 |
| 태스크 문서 | 이 태스크가 **어떤** 테스트를 추가해야 하는지 |
| 스레드 | 실제로 작성하고 통과시킨다 |

이 프로젝트는 T-001~T-005b 동안 세 층이 전부 비어 있었다. 수용 기준 60여 개를
일회성 브라우저 관측으로만 검증했고 재현 가능한 형태로 남은 것이 없었다.
T-005a 가 검증용 하네스를 실제로 만들었지만 요구하지 않아 커밋되지 않고
사라졌다 — **요구하지 않은 산출물은 남지 않는다.**

### 통과하는 테스트는 아무것도 증명하지 않는다

테스트 스위트를 받으면 **일부러 코드를 깨뜨려 실패를 확인한다.** T-008 은
45개를 통과시켰지만, 내가 `resetGame()` 의 `lockResetCount = 0` 을 지웠을 때
45개 전부 그대로 통과했다. 커버리지 구멍이었다.

자식에게도 이것을 요구하라. T-008 수용 기준 7·9 가 "일부러 깨뜨려 실패를
확인하고 원복하라" 였고, 그 과정에서 자식이 **자기 단언이 동어반복이었음**을
스스로 발견했다(기대값을 `CONFIG.B2B_MULTIPLIER` 에서 끌어와, 상수를 2로
바꿔도 통과하는 테스트였다).

### 같은 유형이 세 번 반복되면 개별 테스트를 그만두고 구조를 테스트하라

"상태 필드 초기화 누락" 이 세 번 나왔다: `holdCurrentPiece` 의 `lockTimerMs`,
`resetGame` 의 `combo`/`isBackToBack`/`lastMoveWasRotation`, 그리고 테스트가
못 덮은 `lockResetCount`. 필드를 하나씩 단언하는 테스트는 새 필드가 늘 때마다
또 빠뜨린다.

`test/reset-completeness.test.js` 는 필드를 열거하지 않는다. 갓 로드한 `state`
를 기준으로 삼고 어지럽힌 뒤 재시작한 `state` 와 통째로 비교한다. **새 필드가
추가되면 별도 조치 없이 검사 대상이 된다.** 유형 전체가 닫힌다.

곁들여 두 개의 보조 테스트를 둔다: 어지럽히기가 실제로 필드를 바꿨는지(공허한
통과 방지), 제외 목록의 키가 실재하는지(이름 변경 시 조용히 새는 것 방지).

## 8. 한 사이클 체크리스트

- [ ] 앞 태스크 결과를 보고 이번 태스크 본문을 쓴다
- [ ] 수용 기준이 측정 가능하고 초기 상태가 명시됐는가
- [ ] 회귀 항목이 마지막 기준으로 들어갔는가
- [ ] 알고 있는 함정을 명시했는가
- [ ] Verification 에 시간 대기가 없는가
- [ ] 최종 출력 형식을 지정했는가
- [ ] 태스크 문서를 커밋했는가 (worktree 는 추적 파일만 체크아웃한다)
- [ ] `bb thread spawn --parent-self --new-environment worktree`
- [ ] 산출물 회수 후 **구조를 직접 확인**했는가
- [ ] `git worktree list` 에서 브랜치 이름을 읽어 병합했는가
- [ ] (병렬이었다면) 통합 리뷰를 했는가
- [ ] `docs/tasks/README.md` 상태 갱신, 후속 항목 등록
- [ ] `node --test test/` 통과, 새 순수 함수의 테스트가 추가됐는가
- [ ] 테스트를 일부러 깨뜨려 실패를 확인했는가
- [ ] **병합 먼저, 그 다음** `bb thread archive` → `bb thread stop`

## 9. 아직 검증하지 않은 것

- `--plan` 런타임 승인 모드와 `bb thread interactions approve`
- `bb thread fork` / `edit-message`
- `bb automation` 으로 리뷰나 회귀 검증을 정기 실행
- `.bb-env-setup.sh` (설치할 의존성이 없어 만들지 않았다)
- 렌더링·레이아웃·시각 상태의 자동 검증. 하네스 범위 밖이라 여전히
  스크린샷을 눈으로 본다.
- 터치 제스처 테스트. 하네스의 `performance.now()` 스텁이 0 고정이라 탭과
  스와이프의 시간 판정을 재현할 수 없다.

## 10. 리스크는 소유자가 없으면 영원히 리스크로 남는다

T-001 에서 "자동 테스트 없음" 을 리스크로 적었고, 그 뒤 다섯 사이클 동안
**매번 문서에 다시 적기만 했다.** 리뷰에서 나온 결함(T-006, T-007)은
꼬박꼬박 태스크로 등록했으면서 워크플로 자체의 구멍은 관찰만 했다.
T-008 로 승격하고서야 45개 테스트가 생겼다.

리스크 항목을 적을 때는 **언제 태스크로 승격할지** 함께 적는다. 그러지
않으면 관찰 기록일 뿐이다.
